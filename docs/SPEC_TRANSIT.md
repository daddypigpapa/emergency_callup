# 대중교통 도달범위·예상 도착시간 — 구현명세

본 문서는 `docs/SPEC.md`(이하 본 SPEC)의 하위 명세다. 본 SPEC §0 규칙(허용 의존성, 색 없는 UI, innerHTML 금지, 요청 크기 예산)과 `docs/SPEC_AREA_EDITOR.md`의 격자 정의(§3.1)를 그대로 쓴다.

구현자는 작업 패키지(WP)를 §11 순서대로 진행하고, WP마다 `make lint test`가 통과하는 상태로 커밋한다. **WP0의 실측 결과가 이 문서의 가정과 다르면 다음 WP로 가지 말고 사용자에게 보고한다.**

## 0. 한 줄 요약

버스·도시철도 노선 데이터를 서버에 미리 받아 두고, **(가)** 관리자가 지도에서 찍은 지점에서 출발 시각별로 15·30·45·60분 안에 갈 수 있는 범위를 격자 칸으로 지도에 그리고, **(나)** 발령 중 각 현장인력의 마지막 위치에서 그 조 집결지까지 대중교통 예상 도착시간을 상황판에 보여준다.

## 1. 용어

| 용어 | 정의 |
|---|---|
| 도달범위 | 한 출발점·출발 시각에서 정해진 분 안에 도착할 수 있는 격자 칸의 집합. 15·30·45·60분 4단계 |
| 예상 도착시간(ETA) | 현장인력의 마지막 위치에서 조 집결지까지 걸어서 + 버스·도시철도로 가는 데 걸리는 추정 시간(분) |
| 정류장(stop) | 버스 정류소와 도시철도 역을 함께 부르는 말 |
| 노선 패턴 | 한 노선의 한 방향 정류장 순서. 같은 노선번호라도 상행·하행은 다른 패턴 |
| 배차간격 | 같은 노선 패턴의 차가 오는 간격(분). 평일·토요일·일요일 값이 따로 있다 |
| 요일구분 | `weekday`(평일), `sat`(토요일), `sun`(일요일·공휴일) |

## 2. 결정 사항

1. **데이터는 서버에 내장한다(2026-10-16 사용자 결정, A안).** 발령 중에는 외부 API를 부르지 않는다. 데이터는 관리자가 명령 한 번으로 미리 받아 SQLite에 넣는다(§4). 통신 장애·호출 한도와 무관하게 동작해야 한다.
2. **범위는 대구 먼저, 그다음 인접 시군(사용자 결정).** 1단계는 대구광역시(군위군 포함) 시내버스 + 도시철도 1·2·3호선이다. 2단계는 경산·칠곡·영천·고령·성주·청도 버스다. 데이터 형식이 같으므로 2단계는 도시코드를 추가해 다시 받는 일이다(§11 WP6).
3. **기능은 (가)와 (나) 둘 다 만든다(사용자 결정).**
4. **결과는 추정치다.** 버스는 실제 시간표가 아니라 배차간격 기준으로 계산한다(§5.2). 실시간 버스 위치·도착 정보는 쓰지 않는다. 화면에는 반드시 "추정"이라고 표시한다.
5. **새 Go 의존성은 추가하지 않는다.** 경로 계산은 표준 라이브러리 `container/heap`으로 직접 짠다. OpenTripPlanner 같은 외부 엔진은 쓰지 않는다(Java·수 GB 메모리가 필요해 단일 바이너리 원칙과 맞지 않음).
6. **보정값은 설정으로 둔다.** 버스 평균 속도, 걷기 속도, 대기시간 계수는 실제와 맞춰 고칠 수 있어야 한다(§5.3). 기본값은 추정치이며 실측으로 맞춘다.

## 3. 데이터 출처 (WP0에서 실측 확인할 것)

조사일 2026-10-16. **아래 표의 "확인" 칸이 "미검증"인 항목은 실제 API를 불러 본 적이 없다.** WP0에서 대구 데이터로 실제 호출해 확인한다.

| 데이터 | 출처 | 쓰는 항목 | 확인 |
|---|---|---|---|
| 버스 노선 목록 | 공공데이터포털 `국토교통부_(TAGO)_버스노선정보`(15098529) 노선번호목록 조회 | routeid, routeno, routetp | 오퍼레이션 존재 확인, 대구 응답 미검증 |

| 노선별 정류장 순서·좌표 | 같은 API 노선별경유정류소목록 조회 | nodeid, nodenm, nodeord, gpslati, gpslong, updowncd | 오퍼레이션 존재 확인, 응답 항목 미검증 |
| 도시코드 | 같은 API 도시코드 목록 조회 | citycode, cityname | 대구 = 22로 알려져 있음, 미검증 |
| 도시철도 역·시간표 | 1순위: `국토교통부_(TAGO)_지하철정보` 역별 시간표. 2순위(대구 미제공 시): 대구교통공사 누리집 시간표를 사람이 옮긴 CSV(`transit/daegu_metro.csv`, §4.3) | 역 좌표, 역간 소요시간, 시간대별 배차간격 | **대구 제공 여부 미검증** |

- 인증키: 공공데이터포털 일반 인증키 하나로 위 API를 모두 쓴다. `deploy/key.env`에 `DATA_GO_KR_KEY=` 로 넣는다(값 뒤 주석 금지). 키는 데이터 받기 명령만 쓰고, 서버 실행 중에는 쓰지 않는다.
- 호출 한도: 개발계정 하루 10,000건(포털 표기). 대구 노선 약 130~200개 × (정보 1건 + 정류장 목록 1~2건) ≈ 600건이라 한 번에 받을 수 있다. WP0에서 실제 노선 수를 센다.

### 3.1 WP0에서 반드시 답할 질문

1. 대구(22) 노선정보항목 조회에 배차간격·첫차·막차가 채워져 오는가? 비어 있는 노선은 몇 %인가?
2. 경유정류소목록에 정류장 좌표와 순번이 있는가? 상행·하행이 어떻게 구분되는가?
3. TAGO 지하철정보가 대구 1·2·3호선 시간표를 주는가?
4. 1이 "대부분 비어 있음"이면: 대구 버스정보시스템이나 다른 공공데이터로 배차간격을 얻을 수 있는지 조사해 보고한다. 이 경우 §5.2 계산 방식을 다시 정한다.

## 4. 데이터 받기와 저장

### 4.1 받기 명령

```
bin/server transit sync --city 22            # 대구 버스
bin/server transit sync --metro transit/daegu_metro.csv   # (지하철 API가 없을 때) 도시철도 CSV
```

- `cmd/server`에 하위 명령으로 붙인다(기존 `server admin create`와 같은 방식).
- 한 도시를 받을 때는 **임시 테이블에 다 받은 뒤 한 트랜잭션으로 교체**한다. 중간에 실패하면 기존 데이터를 그대로 둔다.
- 받은 결과를 요약해 출력한다: 노선 수, 정류장 수, 배차간격 없는 노선 수, 좌표 없는 정류장 수.
- 실행 중인 서버는 다음 계산 때 새 데이터를 읽는다(§5.5 그래프 재적재). 서버를 다시 켤 필요가 없다.

### 4.2 테이블 (`internal/store/migrations/004_transit.sql`)

```sql
CREATE TABLE transit_stop (
  id      TEXT PRIMARY KEY,         -- TAGO nodeid 또는 'M:'+역코드
  city    INTEGER NOT NULL,
  name    TEXT NOT NULL,
  lat     REAL NOT NULL,
  lng     REAL NOT NULL,
  kind    TEXT NOT NULL CHECK (kind IN ('bus','metro'))
);
CREATE TABLE transit_pattern (      -- 노선 한 방향
  id         INTEGER PRIMARY KEY,
  city       INTEGER NOT NULL,
  route_id   TEXT NOT NULL,         -- TAGO routeid
  route_no   TEXT NOT NULL,         -- 화면 표시용 (예: 급행1, 1호선)
  kind       TEXT NOT NULL CHECK (kind IN ('bus','metro')),
  first_min  INTEGER,               -- 첫차, 자정 기준 분. NULL = 모름
  last_min   INTEGER,               -- 막차
  hw_weekday INTEGER,               -- 배차간격(분). NULL = 모름
  hw_sat     INTEGER,
  hw_sun     INTEGER
);
CREATE TABLE transit_pattern_stop (
  pattern_id INTEGER NOT NULL REFERENCES transit_pattern(id) ON DELETE CASCADE,
  seq        INTEGER NOT NULL,
  stop_id    TEXT NOT NULL REFERENCES transit_stop(id),
  run_sec    INTEGER,               -- 이전 정류장에서 오는 데 걸리는 초. 도시철도만 채움, 버스는 NULL(§5.2로 계산)
  PRIMARY KEY (pattern_id, seq)
);
CREATE TABLE transit_sync (          -- 마지막으로 받은 때
  city      INTEGER PRIMARY KEY,
  synced_at INTEGER NOT NULL,
  summary   TEXT NOT NULL            -- 4.1 요약 JSON
);
```

### 4.3 도시철도 CSV (지하철 API가 없을 때만)

`transit/daegu_metro.csv` — 저장소에 커밋한다(공개 시간표를 옮긴 것이라 비밀 아님).

```
노선,순번,역이름,위도,경도,이전역에서(초),첫차,막차,평일배차(분),토요일배차(분),일요일배차(분)
1호선,1,설화명곡,35.79..,128.48..,,05:30,23:30,8,10,10
```

- 배차간격은 노선 전체에 한 값만 둔다(첨두·평시 구분은 하지 않음 — 1단계 단순화). 첫 줄의 값만 읽고 이후 줄의 배차 칸은 비워도 된다.
- 상행·하행은 CSV 한 방향에서 서버가 뒤집어 만든다.

## 5. 경로 계산

### 5.1 그래프

- 노드: 정류장.
- 탑승 간선: 노선 패턴의 연속한 두 정류장. 소요시간은 도시철도는 `run_sec`, 버스는 §5.2.
- 걷기 간선: 직선거리 400 m 이내 정류장끼리(환승). 걷는 시간 = 직선거리 × 1.3(우회 계수) ÷ 걷기 속도.
- 출발점 → 정류장: 출발점 반경 800 m 안의 정류장까지 걷기(같은 식).
- 정류장 → 목적지(칸 중심·집결지): 같은 식. 걷기만으로 가는 경우(대중교통을 안 타는 편이 빠름)도 계산한다.

### 5.2 시간 규칙 (빈도 기반)

- 탑승 대기 = 배차간격 × 대기계수(기본 0.5, 평균 대기). 요일구분에 맞는 배차간격을 쓴다.
- 배차간격이 NULL인 노선 패턴은 **기본값 20분**으로 계산하고, 결과에 "배차 정보 없는 노선 포함"을 표시한다. (WP0 결과에 따라 바뀔 수 있다.)
- 버스 정류장 사이 소요시간 = 두 정류장 직선거리 × 1.3 ÷ 버스 평균 속도. 정류 시간 20초를 더한다.
- 운행시간: 정류장에 도착한 시각이 `first_min` 이전이거나 `last_min` 이후면 그 노선은 탈 수 없다. NULL이면 05:30~23:00로 본다.
- 같은 노선을 계속 타면 대기는 한 번만 더한다(정류장마다 다시 기다리지 않음).
- 환승 횟수 제한: 3회.

### 5.3 보정값 (`settings` 테이블, 관리자 설정 화면에서 수정)

| 키 | 기본값 | 의미 |
|---|---|---|
| `transit.walk_kmh` | 4.0 | 걷기 속도 |
| `transit.bus_kmh_peak` | 15 | 버스 평균 속도, 07~09시·17~19시 |
| `transit.bus_kmh_offpeak` | 20 | 그 밖의 시간 |
| `transit.wait_factor` | 0.5 | 대기 = 배차간격 × 이 값 |
| `transit.default_headway` | 20 | 배차간격 모를 때 |

기본값은 추정치다. WP5에서 실제 노선 몇 개를 카카오맵·네이버지도 길찾기 결과와 비교해 맞추고, 비교 결과를 §12에 기록한다.

### 5.4 알고리즘

- 시간 의존 다익스트라(도착 시각을 라벨로, `container/heap`). 상태는 `(정류장, 지금 타고 있는 노선 패턴)`으로 둬서 같은 노선 연속 탑승을 구분한다.
- **(가) 도달범위**: 출발점에서 정방향 1회 탐색 → 최대 60분까지 모든 정류장의 도착 시각 → 칸마다 "가장 가까운 정류장들의 도착 시각 + 걸어서 칸 중심까지"의 최솟값. 칸 크기는 250 m 고정. 칸 후보는 출발점 반경 25 km 안(60분 상한).
- **(나) 예상 도착시간**: 조마다 집결지에서 **역방향 1회 탐색**(도착 시각 기준 거꾸로)으로 모든 정류장의 "여기서 출발하면 집결지까지 걸리는 시간"을 구하고, 각 현장인력은 자기 위치 주변 정류장에서 조회만 한다. 조원이 50명이어도 탐색은 조당 1회.
  - 역방향 탐색의 "도착 기준 시각"은 지금 시각 + 30분으로 둔다(1단계 단순화). 대기 계산은 배차간격 평균이라 정방향과 결과가 크게 다르지 않다.
- 성능 목표: 대구 전체(정류장 약 4,000~5,000개 예상) 한 번 탐색 200 ms 이내. WP2 벤치마크로 확인한다.

### 5.5 메모리 적재

- 그래프는 서버 메모리에 한 벌 둔다. `transit_sync.synced_at`이 바뀌면 다음 요청 때 다시 읽는다.
- 데이터가 없으면(아직 sync 안 함) API는 `409 {"err":"no_transit_data","msg":"대중교통 데이터를 먼저 받으세요"}`.

## 6. 서버 API

| 경로 | 권한 | 요청 | 응답 |
|---|---|---|---|
| `GET /a/transit/isochrone` | operator | `lat, lng, t=HH:MM(생략 시 지금), day=weekday\|sat\|sun(생략 시 오늘)` | `{t, size:250, bands:[{min:15, cells:[[i,j],...]}, {min:30,...}, {min:45,...}, {min:60,...}], estimated:true, missingHeadway:bool, syncedAt}` — 각 칸은 자기가 속한 가장 작은 단계에만 들어간다 |
| `GET /a/transit/eta` | operator | 없음(진행 중 발령) | `{t, members:[[memberId, 분 또는 null], ...], estimated:true, syncedAt}` — 위치 없음·집결지 없음·90분 초과는 null |
| `GET /a/transit/status` | operator | 없음 | `{cities:[{city, name, syncedAt, routes, stops, missingHeadway}]}` |

- 도달범위 응답 크기: 60분이면 칸 수천 개가 나올 수 있다. 칸을 `[i,j]` 정수로 보내고 gzip을 믿는다. 예산 확인: 칸 5,000개 ≈ 60 KB(gzip 전).
- ETA는 위치가 계속 바뀌므로 상황판이 **60초마다** 따로 부른다(3초 델타에 넣지 않는다). 서버는 조별 역방향 탐색 결과를 60초 캐시한다.

## 7. 관리자 화면

### 7.1 상황판 — 도달범위 (가)

- 지도 위 버튼 [대중교통 도달범위]. 누르면 "지도를 클릭해 출발점을 고르세요" 안내와 함께 출발 시각(`<input type="time">`, 기본 지금)·요일구분(`<select>`) 입력이 나온다.
- 지도를 클릭하면 결과를 그린다. 색 없이 선으로만 구분한다:
  - 15분: 굵은 실선, 30분: 실선, 45분: 점선, 60분: 가는 점선.
  - 칸 경계는 기존 `web/shared/grid.js`의 `mergeRuns`·`runToBounds`로 합쳐서 그린다.
- 범례 한 줄: "대중교통 도달범위(추정) · 출발 08:30 평일 · 데이터 2026-10-16".
- [지우기]로 레이어를 없앤다. 발령 여부와 관계없이 쓸 수 있다.

### 7.2 상황판 — 예상 도착시간 (나)

- 조 패널의 인원 줄에 "버스 32분" 같은 글자를 붙인다. 추정치이므로 글자 앞에 `≈`를 붙인다(예: `≈32분`).
- 도착(ARRIVED) 상태인 사람은 표시하지 않는다.
- 데이터가 없거나 null이면 아무것도 표시하지 않는다.

### 7.3 설정 화면

- "대중교통" 영역: 도시별 받은 날짜·노선 수·정류장 수·배차 없는 노선 수(`/a/transit/status`), §5.3 보정값 입력칸.
- 데이터 받기는 화면에 두지 않는다(명령으로만, §4.1). 키를 화면에 노출하지 않기 위해서다.
